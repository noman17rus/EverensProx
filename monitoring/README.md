# Мониторинг домашнего сервера: WDTT и VLESS

Комплект Docker Compose: Grafana, Prometheus, Node Exporter и сборщик WDTT/3x-ui.
Клиенты разделены по протоколам. Нагрузка Linux, сеть и история трафика собираются
каждые 15 секунд. История хранится 30 дней или до достижения лимита Prometheus
5 GB; старые блоки удаляются при достижении первого ограничения.

## Требования

- Linux с Docker Engine и Compose v2; используется сеть хоста, не Docker Desktop.
- WDTT из этой версии исходников, установленный как `wdtt.service`.
- 3x-ui с API `/panel/api/inbounds/list` и `/panel/api/clients/onlines`
  (для старых версий — `/panel/api/inbounds/onlines`).
  У иных форков x-ui совместимость нужно проверить по доступности источника.
- У каждого клиента VLESS отдельный UUID и непустая уникальная метка `email`.
  Метки `email` здесь — имена клиентов, почтовый ящик не требуется.
- Свободные локальные порты 9100, 9810, 9090 и порт Grafana 3000.

## 1. Включить безопасные метрики WDTT

Соберите обновлённый сервер **из всего Go-пакета**, не из одного `server.go`:

```bash
cd WDTT-Plus
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -trimpath -o wdtt-server .
```

Для другого процессора выберите соответствующий `GOARCH`. Обновите существующий
сервер штатным способом установки, сохранив конфигурацию. Инструкция установщика
находится в `WDTT-Plus/server-installer/README.md`; комплект выпуска требует
пересоздания контрольных сумм после сборки. Не подменяйте отдельный бинарник внутри
подписанного/проверяемого комплекта без обновления его контрольных сумм.

Из каталога `monitoring` установите дополнение systemd:

```bash
sudo install -d -m 0755 /etc/systemd/system/wdtt.service.d
sudo install -m 0644 wdtt-monitoring.conf /etc/systemd/system/wdtt.service.d/monitoring.conf
sudo systemctl daemon-reload
sudo systemctl restart wdtt
sudo curl --fail --unix-socket /run/wdtt-metrics/metrics.sock http://localhost/metrics
```

Перезапуск WDTT кратковременно прерывает подключения. Если в существующей службе
уже заданы `RuntimeDirectory`, сохраните их вместе с `wdtt-metrics` в дополнении.
При нестандартном способе запуска вместо переменной окружения можно передать
`-metrics-socket /run/wdtt-metrics/metrics.sock`. Каталог сокета должен принадлежать
пользователю службы и иметь права `0700`. Не размещайте его в каталоге admin-сокета.
При аварийном завершении без systemd перед повторным запуском удалите оставшийся
metrics-сокет **только после остановки сервера**; обычное завершение удаляет его.

Интерфейс поддерживает только `GET /metrics`. Ключ `/etc/wdtt/monitoring-id.key`
генерируется один раз; сохраняйте его при резервном копировании, чтобы сохранить
идентификаторы клиентов. Пароли, UUID, IP устройств и VK-хеши не экспортируются.
Отдельные подписи клиентов (`label`, `email`) выводятся как имена: не записывайте
в них секреты. Общий доступ WDTT учитывается целиком, включая все его устройства.

## 2. Настроить панель и секреты

```bash
cd monitoring
cp .env.example .env
install -d -m 0700 secrets
umask 077
read -r -p 'Логин 3x-ui: ' xui_user
read -r -s -p 'Пароль 3x-ui: ' xui_pass; printf '\n'
# JSON escaping is handled by Python, including special characters in passwords.
printf '%s\0%s' "$xui_user" "$xui_pass" | python3 -c 'import sys,json; u,p=sys.stdin.buffer.read().decode().split("\0",1); print(json.dumps({"username":u,"password":p}))' > secrets/xui_auth.json
unset xui_user xui_pass
openssl rand -base64 32 > secrets/grafana_password
# Grafana runs as UID 472; Compose mounts the file with host permissions.
# The enclosing secrets directory remains root-only (0700).
chmod 0444 secrets/grafana_password
```

В новых 3x-ui используйте отдельный API-токен, созданный в настройках панели.
В 3x-ui 3.11 для чтения клиентов нужна область `admin`: область `monitor`
разрешает только общие показатели сервера. Административный токен технически
позволяет изменять панель, хотя сборщик вызывает только методы чтения.
Вместо логина и пароля запишите в `secrets/xui_auth.json`
JSON вида `{"token":"ВАШ_ТОКЕН"}`. Токен и пароль не смешиваются. Режим токена
не требует отключения 2FA и не пытается войти через пароль.

В `.env` задайте `XUI_BASE_URL` с портом и полным web base path вашей панели,
например `http://127.0.0.1:2053/my-panel-path`. Для HTTPS используется обычная
проверка сертификата; её отключение не предусмотрено. При включённой двухфакторной
авторизации используйте отдельный токен: ввод одноразовых кодов не реализован.

По умолчанию Grafana слушает `127.0.0.1:3000`. Для прямого доступа из домашней сети
задайте в `GRAFANA_BIND_ADDRESS` конкретный локальный адрес сервера. Не задавайте
публичный адрес или `0.0.0.0`. Для доступа через интернет используйте VPN либо
SSH-туннель, сохранив loopback-привязку:

```bash
ssh -L 3000:127.0.0.1:3000 user@server
```

Файлы секретов исключены из Git. Compose передаёт их сборщику и Grafana как файлы,
а не переменные окружения. Авторизация панели нужна только сборщику; браузер
и Grafana не получают её секреты. Сборщик использует токен либо сессию;
вызывает только вход и методы чтения, включая POST `/onlines`.
В версиях с общими клиентами одна запись трафика может возвращаться на нескольких
inbound: сборщик учитывает её один раз по ID записи. Клиенты VLESS группируются
по `email`; их трафик не удваивается из-за нескольких способов подключения.
Не публикуйте каталог мониторинга через веб-сервер: `.env` содержит путь панели.

## 3. Запуск и проверка

```bash
docker compose config --quiet
docker compose up -d --build
docker compose ps
curl --fail http://127.0.0.1:9810/metrics
curl --fail http://127.0.0.1:9090/-/ready
```

Откройте Grafana по выбранному адресу на порту 3000. Логин `admin`, первоначальный
пароль — содержимое `secrets/grafana_password`. Панель
**EverensProx → Домашний сервер · WDTT и VLESS** подключается автоматически.
Изменение файла первоначального пароля после создания базы Grafana не меняет
пароль существующей учётной записи: его меняют через Grafana.

В начале панели источники `wdtt`, `vless` и `host` должны иметь значение `1`.
Отдельный индикатор показывает работоспособность определения онлайн. Если метод
онлайн отсутствует в версии панели, трафик продолжает собираться, но статус
клиентов остаётся неизвестным. Для диагностики:

```bash
docker compose logs --tail 100 collector
curl --fail http://127.0.0.1:9090/api/v1/targets
```

Подключите один клиент каждого протокола, передайте данные, затем отключите его.
Проверьте рост счётчиков, ненулевую скорость и смену онлайн. Несколько рабочих
соединений WDTT должны давать одного клиента онлайн и отдельное число соединений.
Проверяйте `docker compose restart`: история и идентификаторы должны сохраняться.
Полная проверка после обновления WDTT: `go test ./...` на Linux в `WDTT-Plus`.
Тесты сборщика: `go test ./...` в `monitoring/collector`.

## Как читать показатели

- `down` — к клиенту, `up` — от клиента, для обоих протоколов.
- `vpn_client_traffic_bytes_total` — накопленные счётчики источника. Скорость и
  расход за период считаются через `rate` и `increase`, которые учитывают сбросы.
  Прирост между опросами, совпавший со сбросом, восстановить точно нельзя.
- `vpn_client_online` для WDTT — наличие авторизованных рабочих соединений.
  Для VLESS это критерий онлайн установленной панели, а не число устройств.
- `vpn_source_up` — доступны клиенты и трафик; `vpn_source_online_up` — доступен
  статус онлайн. Ошибки не подменяются нулевым трафиком или статусом «офлайн».
- У нового клиента VLESS счётчики могут появиться позже, чем запись клиента.
  До первого ответа панели с его трафиком значение остаётся неизвестным.
- Показатели сетевых карт включают другие службы, заголовки и повторную передачу.
  Не складывайте трафик всех физических и туннельных интерфейсов: получится
  двойной учёт. В легенде можно выбрать нужный внешний интерфейс.
- История начинается с запуска мониторинга. Оценка расхода за выбранный период
  не восстанавливает прошлое из суммарных счётчиков.
- Изменение имени WDTT сохраняет ID, но начинает новые серии с новой подписью;
  смена пароля WDTT или метки `email` VLESS создаёт новый ID. При миграции
  сохраняйте ключи идентификации и постоянные тома.

Остановка без удаления истории: `docker compose down`. Для резервного копирования
сохраните постоянные тома, настройки, секреты и ключ WDTT. Команда
`docker compose down -v` удаляет историю и ключи сборщика.
